## 변경 이력 (Changelog)

### v1.0 (2026-07-30) — 중간보고 기준선 · 구현 실측 전면 정합

> v0.5(2026-07-24~28)는 dev 브랜치에만 머물러 **main 배포된 적이 없다**(released 최신 = v0.48). 따라서 v0.5를 별도 릴리스로 archive에 등재하지 않고 **v1.0에 흡수**한다 — 아래 v0.5 항목도 v1.0과 함께 처음 배포된다. 이번 회차에서 새로 정합한 항목:

**1. PG 결제 — Out-of-Scope → 토스페이먼츠 샌드박스 구현** · (§2.3·§2.4·FR-1·FR-8·FR-9)

- v0.5까지 "결제는 Out-of-Scope, '업그레이드 문의' 버튼으로 대체"였으나 **실제로는 토스페이먼츠 결제창 연동이 구현**됐다(`payment` 패키지 · `V20__create_payments`). 문서를 구현에 맞춘다.
- 구독 라이프사이클 파생 기능까지 함께 반영: 청구주기(`V27`) · **예약 하향**(`V30 scheduled_plan_changes`) · **미결제 유예**(`V33 payment_pending_until`)
- 알림 타입 3종 추가: `PLAN_EXPIRED` · `PLAN_DOWNGRADED` · `PLAN_DOWNGRADE_FAILED`
- **범위 한정**: **샌드박스(테스트 키) 구현**이며 실 PG 계약·라이브 키 전환은 미완, 결제창 E2E 실검증도 잔여(§11 오픈이슈)

**2. 탐지 모델 — YOLOv8-seg 단일 → U-Net + YOLO 하이브리드** · (FR-3·§6·§7)

- **균열 = U-Net(`crack_unet_resnet34.pt`)**, 박리박락·철근노출 = YOLO — PR #973에서 균열만 교체(v0.5의 "단일 모델 커버" 서술 폐기)
- 등급 산정 단위도 "이미지당 최대 인스턴스 1개" → **"이미지 전체(레터박스 콘텐츠 영역) 마스크 합"**
- 위 두 변화로 v1 임계값이 과대경고(보통 150장 중 83장이 D·E)를 내 **v2 재캘리브레이션**(AI Hub 아파트 균열 470장 재측정, 2026-07-27)

**3. Flyway 도입 완료** · (§6.3·§11)

- v0.5의 "근본 재발 차단은 Flyway 도입(#359)" 미래형 서술 → **완료(#544)**. `V1~V34` 운영, `ddl-auto=validate`, CI에 baseline 정합 통합테스트

**4. 신규 기능 반영(PRD에 항목 자체가 없던 것)**

- **상담원 전용 콘솔**(`/counsel-console`) — 플랫폼 관리자 콘솔 안의 메뉴가 아니라 **COUNSELOR 역할 전용 제3의 셸**(전용 로그인 + 대기열 + 1:1 채팅). 플랫폼 관리자 쪽은 별도로 "상담 관리"(날짜별 조회·읽기전용 대화 열람) (FR-7·FR-8-B·§4)
- **조치 등록 이력**(`V32 defect_action_logs`) — 조치중 단계에서 여러 번 등록되는 사진·조치내용이 단일 스냅샷 컬럼에 덮어써지던 문제를 append-only 테이블로 해소 (FR-4·§6.3)
- **공개 플랜 카탈로그 API** — 랜딩 요금제가 하드코딩에서 **DB `plans` 조회**로 전환. 요금제의 단일 진실은 이제 DB (§2.4)
- **LangSmith PII 제외** — 트레이싱 페이로드에서 개인정보 마스킹·제외 (§6.2)
- **국세청 사업자 실존확인 API** — OCR에 더해 진위확인·상태조회 연동(미등록/휴업/폐업 판정, API 미설정 시 fail-open) (FR-1)

**5. 메뉴 구성(IA) 재구성** · (§4·FR-8-B)

- **플랫폼 관리자 — "서비스 통계" → "대시보드"로 개칭 + 최상위 배치**(로고 클릭·인덱스 진입도 대시보드로)
- **플랫폼 관리자 — 하자 유형·등급 관리 메뉴 삭제**: v0.5의 "향후 개발 이관" 서술을 실제 메뉴·라우트 제거로 확정
- **점검 주기 설정 — 시설물 관리 → 점검 관리로 이동**

**6. 오픈 이슈 정리** · (§11)

- 해소: **#4**(상담원 역할 주체 — COUNSELOR 전용 콘솔·스킬 관리 구현으로 "관리자 겸임" 전제 자체가 변경) · **#10**(보고서 편집기 블로커였던 `/analyze` 구현 완료) · **#11**(`FacilityResponse.latestInspectionId` 추가로 선행 조건 해소)
- 재서술: **#8**(ARM 추론 최적화 — U-Net 전환으로 ONNX 전제 변동)
- 신규: 결제 라이브 전환 잔여 과제

### v0.5 (2026-07-24) — 구현 실측 정합

> 스프린트2 진척으로 문서와 코드가 벌어진 지점을 실측대로 정정하고, 미구현·보류는 "후속"으로 태그했다. 담당자별 반영 항목:

**1. 플랫폼 관리자 경로 분리** — 김승현 · (FR-1·FR-8·§4)

- 진입 경로 `/admin` → `/platform-admin` (로그인 `/platform-admin/login`)
- 로그인 성공 계정이 `PLATFORM_ADMIN`이 아니면 거부

**2. 관리자 콘솔 메뉴 재구성** — 김승현 · (FR-8·§4)

- 기업 관리자 = 사용자 관리 · 플랜/쿼터 관리
- 플랫폼 관리자 = 사용자 관리 · 플랜/쿼터 관리 · 상담 관리 · RAG 문서 관리 · 서비스 통계 · 시스템 모니터링
- 하자 유형·등급 기준 관리는 **"향후 개발"로 이관**

**3. 조직 모델 정정** — DB 스키마 · (§2.4·§6.3)

- `companies` · `company_memberships`(초대/승인 워크플로) 테이블 실재 → "별도 companies 테이블 없이" 단순화 서술 폐기
- `facilities` 소유 주체를 회사로 전환(#660)
- 승격 #531 스키마 정합 핫픽스(`lock_version` 낙관적 락 · `rag_documents.verification_status`) 반영

**4. 시설물 등록/점검 관리 실측** — 허남/오영석 · (§4·§6.3)

- 초기등급 · 담당자 · 메모 필드 확장, 주소검색 + Geocoder 좌표 자동화
- `GET /api/facilities/assignable-users` 신규
- 다가오는 점검 전용 페이지 · 회차 비교 KPI/차트/PNG · 점검주기 전체현황 테이블

**5. 하자 관리 재해석** — 유병현 · (§4·FR-4)

- 하자 단건 목록 → **점검(Inspection) 단위 그룹 목록 + 점검 상세 → 하자 상세 모달 2단계**
- 조치 결과 등록(`PATCH /api/defects/{id}/action`) · 활동 기록 타임라인 · `GET /api/inspections` 신규

**6. 지도 뷰·랜딩** — 김관영 · (§2.3·§4)

- 지도 좌표 = 카카오맵 Geocoder(주소→좌표)로 구현 (EXIF GPS 자동추출은 미채택 → §11 오픈이슈)
- 이용약관 · 개인정보처리방침 라우트 신설

**7. AI 보고서/저장 방어로직 실측** — 김관영 · (FR-5)

- 프롬프트 인젝션 방어 · 인용 검증 · 백엔드 프록시 · 이중 Rate Limit · 내부 인증 헤더
- DRAFT/FINALIZED 상태 · 유니크 제약 · PDF 매직넘버 · 낙관적 락 · path traversal 차단

**8. 황승현 영역 현실 정정 (불일치 → 후속)** — 황승현 · (FR-2·FR-3·§6)

- 영상 프레임 추출 미구현(이미지 전용) · ONNX+INT8 미적용(현재 raw PyTorch)
- FastAPI 워커 단일 프로세스 · 청크 업로드 = 단일 요청 + 진행률 · 점검 생성 담당자 = 본인 자동배정

**9. 상담 내역 통합** — 정재봉 · (§4)

- 마이페이지 · 고객지원 이원화 → **고객지원으로 단일화**

**10. 담당자 이관** — 이은석 · (§7)

- RAG 문서 관리 · 상담 관리 담당 김승현 → **이은석**(고객지원 RAG 챗봇 오너와 통합)

**11. AI 오케스트레이션·관측 도입 (LangGraph·LangSmith)** — 오영석 · (§6·§6.2·FR-5·FR-6)

- **LangSmith 트레이싱**(관측, #717) — `get_llm()` 자동 계측, docker-compose `fastapi`에 env 연결
- **report_chain LangGraph StateGraph**(#703) — grounding 재시도 `while` 루프 → 조건부 엣지 cycle(재시도가 트레이스에 개별 단계로 노출)
- **rag_chat_chain LangGraph StateGraph**(#710) — 단발 파이프라인을 그래프로 감싸고 캐시 히트/검색 0건 조건부 엣지
- 공용 의존성 조합 고정(`langchain 0.3.30`·`langchain-core 0.3.86`·`langsmith 0.10.10`·`langgraph 0.6.11`), `requirements.txt` 변경은 사람 수동 머지

## 1. 개요 (Overview)

건물 외벽·교량 등 시설물을 촬영한 **이미지/영상을 웹 플랫폼에 업로드**하면, AI(딥러닝 비전 모델)가 균열·박리박락·철근 노출 하자를 자동 탐지하고, LLM(LangChain + RAG)이 점검 보고서 초안을 자동 생성해 주는 시설물 안전점검 지원 플랫폼.

### 1.1 배경 및 문제 정의

- 100m 이상 고층 건물 외벽, 고속도로 교량 하부 등은 사람이 직접 점검하기에 **추락 위험, 고비용, 장시간 소요** 등 부담이 크다.
- 육안 점검은 점검자 숙련도에 따라 판독 편차가 크고, 점검 이력이 체계적으로 축적되지 않는다.
- 국내(뷰메진 VODA, 드론와이드샷)·해외(Inspekt AI, Hammer Missions) 모두 촬영 이미지 기반 AI 시설물 점검 서비스가 상용화 단계에 있어 시장성이 검증된 주제다.

### 1.2 솔루션 요약

1. 촬영된 시설물 이미지/영상 **업로드** (촬영 수단 무관)
2. AI 모델(FastAPI 서빙)이 하자 **자동 탐지·분류·심각도 평가**
3. 결과를 웹 대시보드에서 **시각화**(원본 위 바운딩박스/세그멘테이션 오버레이)
4. LangChain 기반 LLM + RAG(점검 법규·기준 VectorDB)로 **점검 보고서 초안 자동 생성**
5. 점검 이력 축적 및 이전 점검 대비 변화 추적
6. **시나리오 챗봇 + 상담원 연결**로 사용 문의·점검 상담 지원

## 2. 목표 (Goals)

### 2.1 프로젝트 목표

- 4주 내 업로드→탐지→시각화→보고서 생성의 **End-to-End 데모 완성**
- 하자 탐지 모델 성능 목표: 균열 탐지 기준 **mAP@0.5 ≥ 0.7** (공개 데이터셋 기준, 팀 협의로 조정)
- 보고서 초안 생성 소요: 이미지 100장 기준 **10분 이내**

### 2.2 목표 사용자 (Persona)

| 페르소나 | 설명 | 핵심 니즈 |
|---|---|---|
| 안전점검 기술자 | 시설물 안전점검 업체 소속, 촬영 결과 판독 | 판독 시간 단축, 누락 방지 |
| 시설물 관리자 | 건물주·관리사무소·도로공사 담당자 | 상태 한눈에 파악, 이력 관리 |
| 점검 책임자 | 보고서 결재·제출 담당 | 법규 기준에 맞는 보고서 신속 작성 |
| 서비스 관리자 | 플랫폼 운영자 | 사용자·콘텐츠·상담 관리 |

### 2.3 범위 정의

**In-Scope (P0 — 필수)**

- 랜딩 페이지(로그인 전 — 서비스 소개·요금제·시작하기)
- 소셜 로그인(Kakao/Google OAuth2) + 마이페이지
- 시설물(프로젝트) 관리
- 이미지 업로드 및 전처리 (영상→프레임 추출은 후속 범위 — v0.5, FR-2)
- AI 하자 탐지: 균열(crack) 중심 + 박리·박락, 철근 노출 — **3종 다중 클래스 확정**(§FR-3)
- 탐지 결과 시각화(오버레이, 확대, 하자별 필터) 및 수동 검수
- 하자 심각도 등급 분류
- LLM 점검 보고서 초안 자동 생성(LangChain) + PDF 내보내기
- RAG 기반 점검 기준 Q&A 챗봇 (LangChain + Chroma)
- 시나리오 챗봇 + 상담원 연결(실시간 채팅)
- 관리자 페이지(사용자·하자 기준·상담 관리)

**P1 — 여유 시 추가**

- 점검 이력 비교(동일 시설물 회차 간 하자 변화 추적)
- 하자 통계 대시보드(유형별/등급별/구역별)
- 균열 폭·길이 정량 추정(픽셀→실측 환산)
- **점검 계획·주기 관리**(FMS 패턴): 시설물별 점검 주기 설정, 다음 점검일 도래 대시보드 표시
- **지도 뷰**: 시설물을 지도(Kakao Map)에 마커 표시, 하자 최고 등급별 색상(녹/황/적) — **좌표는 시설물 주소를 카카오맵 Geocoder로 변환**(v0.5 실측, EXIF GPS 자동추출은 미채택 — §11 오픈이슈)
- **인앱 알림 센터**: 헤더 벨 아이콘 + 알림 목록 — 분석 완료, 검수 대기, 상담 답변, 점검일 도래(주기 연계). 인앱 폴링 기반, 이메일·푸시는 제외
- **멤버십 쿼터**: 플랜별 사용량 제한(월 분석 장수 등) 체크 + 요금제 소개 페이지 + 마이페이지 "내 플랜" (§2.4)
- **구독 결제(토스페이먼츠 샌드박스)** — v1.0 신규: 플랜 업그레이드 시 결제창 호출 → 승인(confirm) → 플랜 반영, 결제 이력 조회, 청구주기·**예약 하향**·**미결제 유예** 처리 (§2.4). **샌드박스 한정** — 실 PG 계약·라이브 키 전환은 범위 외(§11)
- **메뉴별 경량 AI 기능** (전원 AI 구현 경험 목적 — 각 프롬프트 체인 1개 수준): 대시보드 AI 주간 브리핑, 하자 AI 설명 패널, 하자 자연어 검색 — **Standard 이상 플랜 전용**(§2.4 프리미엄 전략)

**P2 — 확장 목표 (Stretch)**

- **불법 증축 탐지**: 건축물대장/기준 형상 대비 외형 변화 탐지
- 외벽 3D/파노라마 매핑, 열화상 이미지 분석
- 체크리스트 기반 점검(사전점검 앱 패턴 — AI 중심 흐름과 결이 달라 참고 수준)
- **조치 보드(칸반)**: 하자 상태머신을 칸반 보드로 시각화, 드래그로 상태 전이

**Out-of-Scope**

- 촬영 장비(드론 등) 연동·제어
- 법적 효력을 갖는 정식 안전진단 판정(본 시스템은 **점검 보조 도구**)
- **실 PG 계약·라이브 결제**(v1.0 개정) — 결제 자체는 **토스페이먼츠 샌드박스로 구현됨**(P1, §2.4)이나, 사업자등록 기반 실 계약·라이브 키 전환·실청구는 이번 범위 외. 라이브 전환 전제 조건은 §11 오픈이슈 참조
- 정기 자동결제(빌링키 기반 자동 갱신) — 현재는 결제창 방식의 건별 승인만. 만료 시 유예·하향으로 처리(§2.4)

### 2.4 비즈니스 모델 (멤버십·구독)

**목표 고객(B2B)**: 시설물 안전점검 업체, 건물·자산 관리업체, 지자체 시설 관리 부서

**설계 원칙 — 역할과 플랜의 축 분리**: 역할(Role)은 "무엇을 할 수 있는가"(권한, FR-1), 플랜은 "얼마나·누구와 쓸 수 있는가"(용량·좌석·프리미엄 기능). 두 축은 겹치지 않으며, **좌석(점검자 초대 수)이 두 축을 잇는 다리** — Free는 1인 체험, Standard부터 팀 협업(검수 워크플로)이 열린다.

**요금제(안)** — 과금 축: 시설물 수 + 월 분석 이미지 수 + 점검자 좌석 (실원가인 HF API 토큰·스토리지·분석 컴퓨팅과 비례)

| 플랜 | 월 가격 | 시설물 / 월 분석 | 점검자 좌석 | 보고서 | 상담 | AI 부가 기능* | 대상 |
|---|---|---|---|---|---|---|---|
| Free | ₩0 | 1개 / 50장 | ✕ (1인 계정) | 워터마크 | 시나리오 챗봇만 | ✕ | 체험·개인 |
| Standard (월 구독) | **₩29,000** | 10개 / 1,000장 | 3명 | 정식 PDF | 상담원 연결 | ⭕ | 소규모 점검 업체 |
| Enterprise (월 구독) | **₩59,000** | 무제한 / 협의 | 무제한 | + 데이터 반출 | 우선 응대 | ⭕ | 관리업체·공공 |

*AI 부가 기능 = P1 경량 AI(하자 설명·자연어 검색·주간 브리핑)와 회차 비교 — "핵심 AI 탐지는 전 플랜, AI 편의 기능은 유료" 프리미엄 전략(HF 토큰 원가와 비례)

> **⚠️ 요금제 단일 진실 = DB `plans` 테이블**(v1.0 신규). 위 표는 정책 설명용 스냅샷이며, 랜딩 요금제 섹션은 하드코딩이 아니라 **공개 플랜 카탈로그 API**(비인증 조회)로 DB에서 렌더한다 — 한도·기능 플래그(`max_facilities`·`max_monthly_analyses`·`max_seats`·`has_pdf_watermark`·`has_counselor_access`·`has_ai_addon`)를 바꿀 때는 **DB(시드 마이그레이션)가 기준**이고 이 표는 따라 갱신한다. 문서와 DB가 어긋나면 DB가 맞다.

**조직 모델**(v0.5 정정 — 구현 실측): 초기 "별도 조직 테이블 없이 `company_id`만 공유"로 단순화했으나, 실제 구현은 **`companies`(기업) + `company_memberships`(소속·초대·승인) 테이블**로 확정됐다. `company_memberships`는 `status`(PENDING/APPROVED/REJECTED/REVOKED/EXPIRED) 상태머신으로 **좌석 초대·승인 워크플로**를 관리하며, 사용자당 APPROVED 소속은 1개로 제약(부분 유니크 인덱스). **`facilities`의 소유 주체도 개인이 아닌 회사로 전환**(#660) — 점검 생성·담당자 배정은 회사 소속 한정. 여전히 "계정 소유자 = 플랜 보유자, 소유자가 점검자를 좌석 한도 내 초대"라는 §2.4 과금·좌석 원칙은 유지되지만, 그 구현 그릇이 컬럼 공유가 아니라 정규 테이블이라는 점을 반영

**구현 범위**: 플랜 테이블·사용량 쿼터 체크(`QuotaInterceptor` — 역할 체크와 분리)·좌석 관리·요금제 페이지·마이페이지 플랜 표시까지 P1, 쿼터/좌석 초과 시 업그레이드 안내 모달 표준 UX. **결제는 v1.0에서 토스페이먼츠 샌드박스로 구현**(아래 참조 — v0.5까지의 "업그레이드 문의 버튼 대체" 방침 폐기)

**구독 결제 — 토스페이먼츠 샌드박스**(v1.0 신규): 플랜 업그레이드는 문의 버튼이 아니라 **실제 결제 플로우**로 처리한다.

- **플로우**: 주문 생성(서버가 주문 식별자·금액 확정) → 토스 결제창 호출(SDK) → 리다이렉트(성공/실패) → **서버 승인(confirm)** → 플랜 반영 + 결제 이력 기록. 금액·플랜은 **서버가 확정한 주문 기준**으로만 승인한다(클라이언트 전달 금액 신뢰 금지)
- **구독 라이프사이클**: 청구주기 관리 · **예약 하향**(상위→하위 변경은 잔여 기간을 보장하고 다음 주기에 반영) · **미결제 유예**(유료→유료 하향 시 결제 실패해도 즉시 강등하지 않고 유예 기간 부여, 킬 스위치 기본 닫힘) · 만료 시 하향. 각 전이는 알림으로 통지(FR-9)
- **범위 한정**: **샌드박스(테스트 키)** 구현이며 실 PG 계약·라이브 키 전환은 Out-of-Scope. 라이브 전환 시 "PG에는 승인됐으나 응답만 유실된 결제"의 복구 경로가 선행 필수 — 미비 상태로 전환하면 실청구를 은폐할 수 있다(§11 오픈이슈)
- 키는 전부 env 주입(`.env`), 미설정 시 **결제 진입점만 비활성**되고 서비스 전체 배포는 성공하도록 소프트 가드(결제는 부가기능이라는 판단)

**Free 즉시 체험**(v0.47 신규): Free 플랜은 관리자 승인 대기 없이 **회원가입 완료(이메일 인증 통과) 즉시 활성화** — 사업자등록번호 인증 여부와 무관하게 바로 체험 가능

**사업자등록번호 인증 — 가입 시 선택, 업그레이드 시 게이트**(v0.47 신규, **v1.0 개정**): 회원가입 시 사업자등록번호 인증은 **선택사항**(미인증 상태로도 가입·Free 이용 가능, `users.business_verified = false`). Free → Standard/Enterprise **업그레이드 시도 시** `business_verified` 확인 → **false면 사업자등록번호 인증 절차로 유도**(인증 통과 후 업그레이드 진행), **true면 바로 진행**. **v1.0**: 결제가 실제로 구현됐으므로 이 게이트는 "문의 접수 전 확인"이 아니라 **결제 진입 전 게이트**로 작동한다

**사업 목표(가설)**: 점검 1건당 판독 인건비 대비 절감 효과를 근거로 Standard(월 ₩29,000) 전환을 유도하고, 팀·다지점 운영 고객은 Enterprise(월 ₩59,000)로 유도 — 완료보고 시 원가·손익 시뮬레이션 1장 포함(v0.44: 고정가 확정으로 시뮬레이션 기준 단가 확보)

## 5. 핵심 기능 요구사항

### FR-1 소셜 로그인 & 마이페이지

- Kakao / Google OAuth2 로그인 (Spring Security OAuth2 Client)
- 세션 관리: Spring Session + Redis
- 마이페이지: 프로필 조회·수정, 소셜 계정 연동 관리, 내 점검 이력·보고서·상담 내역 조회, **내 플랜·사용량 표시 + 점검자 좌석 초대 관리(P1, §2.4)**
- 역할(Role): 일반 사용자 / 점검자 / 관리자 / 상담원 / **플랫폼 관리자**(v0.47 신규) — 계층: `ADMIN > INSPECTOR > USER`, `COUNSELOR`는 별도 축(관리자 겸임 가능). **`PLATFORM_ADMIN`은 위 계층과 분리된 별도 축**(B2B SaaS 플랫폼 운영진 전용, 기업 소속이 아니므로 `company_id` 없음) — 기존 `ADMIN`은 이제 **기업 관리자**(자기 `company_id` 범위 내 전체 권한)로 재정의
- **역할별 권한 매트릭스**:

| 기능 | 일반 사용자 | 점검자 | 상담원 | 기업 관리자 | 플랫폼 관리자 |
|---|---|---|---|---|---|
| 시설물 등록·조회 | 본인 소유만 | 배정 시설물 | ✕ | 전체(자기 `company_id`) | ✕ (운영 대상 아님) |
| 업로드·분석 요청 | ⭕ (플랜 쿼터 내) | ⭕ | ✕ | ⭕ (자기 `company_id`) | ✕ |
| **검수(오탐 수정·등급 확정)** | ✕ | ⭕ 핵심 권한 | ✕ | ⭕ (자기 `company_id`) | ✕ |
| 하자 상태 전이 | 조치 완료 보고만 | ⭕ | ✕ | ⭕ (자기 `company_id`) | ✕ |
| 보고서 생성·편집 | 열람·다운로드만 | ⭕ | ✕ | ⭕ (자기 `company_id`) | ✕ |
| 상담원 콘솔 | ✕ | ✕ | ⭕ 전용 | ✕ | ⭕ (전체) |
| 기업 관리자 페이지 | ✕ | ✕ | ✕ | ⭕ 전용(자기 `company_id`) | ✕ |
| 플랫폼 관리자 페이지(`/platform-admin`) | ✕ | ✕ | ✕ | ✕ | ⭕ 전용(전체 기업) |

- **권한 집행 원칙**: 프론트 메뉴 숨김(`ProtectedRoute`/`AdminRoute`)은 편의일 뿐 — 백엔드에서 `@PreAuthorize`(역할) + 소유권 데이터 필터를 반드시 병행. 플랜 제한은 별도 `QuotaInterceptor`로 분리(§2.4)
- **CSRF 방어**: 쿠키 세션 기반이므로 상태 변경 요청(POST/PUT/PATCH/DELETE)에 Spring Security CSRF 토큰 적용 — React는 `XSRF-TOKEN` 쿠키를 읽어 헤더로 전송
- **기업회원 ID/PW 로그인**(v0.43 신규): 사업자등록증 OCR 인증으로 가입한 기업회원은 소셜 로그인 대신 아이디/비밀번호 자체 로그인 사용(스토리보드 AUTH-01 기업회원 탭). 비밀번호는 BCrypt 해시 저장, 평문 저장·로그 노출 금지
- **가입 시 사업자등록번호 인증 선택제 + Free 즉시 체험**(v0.47 개정): 사업자등록번호 인증(OCR)은 **가입 시 선택사항**으로 전환 — 미인증 상태로도 가입 및 Free 플랜 즉시 이용 가능(승인 대기 없음). 인증 여부는 `users.business_verified`로 관리하며, 유료 플랜 업그레이드(결제 진입) 시점에 게이트로 작동(§2.4)
- **사업자등록증 OCR + 국세청 실존확인 API**(v1.0 실측 반영): 사업자등록증 이미지에서 사업자등록번호·대표자명·상호를 **OCR로 추출**(FastAPI 체인)하고, 국세청 API로 **진위확인(대표자명·개업일 대조) + 상태조회(미등록/휴업/폐업 판정)**를 수행한다.
  - **판정 결과에 따른 분기**: 진위 불일치·휴업·폐업·미등록 → 인증 실패(가입 차단). **API 키 미설정·외부 장애 → fail-open**(`SKIPPED`)으로 `business_verified = false` 상태로 가입은 계속 진행 — 외부 의존성 장애가 가입 자체를 막지 않게 한다. "인증 선택제"(위 항목)는 이 fail-open과 미인증 가입 허용을 뜻하며, **실제 불일치가 검출된 경우는 통과시키지 않는다**
  - 사업자등록번호는 하이픈 제거 정규화 후 저장·중복검사
- **구독 결제**(v1.0 신규): 마이페이지 "내 플랜"에서 업그레이드 시 토스페이먼츠 결제창 호출 → 서버 승인 → 플랜 반영. 결제 이력 조회, 예약 하향 확인·취소 제공(§2.4)
- **플랫폼 관리자 로그인**(v0.47 신규, **v0.5: 경로 `/admin` → `/platform-admin` 분리**): `/platform-admin/login` 접속 시 기업회원·일반 로그인 화면과 **분리된 플랫폼 관리자 전용 로그인 페이지** 노출. 로그인 성공 시 계정 역할이 `PLATFORM_ADMIN`이 아니면 **로그인 거부**(기업회원·일반 사용자는 이 진입점으로 접근 불가). 플랫폼 관리자 계정은 자체 가입 없이 **초기 시드 데이터로 생성**(운영진 발급), ID/PW 로그인 + Spring Session
- **기업회원 가입 — 이메일 인증**(v0.45 신규, **Spring Mail SMTP**): 사업자등록증 OCR 인증에 더해 가입 이메일 소유 확인을 위한 인증코드(6자리 숫자) 발송·검증 통과 시 가입 완료 처리. 인증코드는 Redis에 `email:verify:SIGNUP:{email}` 키로 저장(아래 공통 규약 참조)
- **아이디 찾기 / 비밀번호 찾기**(v0.45 개정 — **이메일 인증 코드 방식으로 전환, Spring Mail SMTP**): 이메일 입력 → 인증코드(6자리 숫자) 발송(아이디 찾기는 PURPOSE=FIND_ID, 비밀번호 찾기는 PURPOSE=RESET_PW) → 사용자가 코드를 직접 입력해 검증 → 성공 시 **동일 세션 내에서 즉시** 아이디 마스킹 표시(예: `abc***@company.com`) 또는 새 비밀번호 설정 화면으로 진행. 계정 미존재 시에도 "인증코드를 발송했습니다" 등 동일한 응답을 반환해 계정 존재 여부 비노출. 비밀번호 재설정 완료 후 기존 세션 전체 무효화(재로그인 요구). (v0.43의 사업자등록번호 대조 방식은 본 방식으로 대체)
- **이메일 인증 공통 규약**(v0.45 신규 — SIGNUP/FIND_ID/RESET_PW 3개 화면 공용): Redis 키 `email:verify:{PURPOSE}:{email}`(PURPOSE enum: SIGNUP/FIND_ID/RESET_PW) · 값 = 6자리 랜덤 숫자(또는 검증용 해시) · **TTL 5분**(Redis 자체 만료 — 별도 배치/스케줄러 불필요) · **1회성**: 검증 성공 시 즉시 삭제(재사용 방지) · **실패 횟수 제한**: 같은 키에 attempt count 병행 저장, **5회 실패 시 코드 재발급 강제**(무차별 대입 방지) · **재발송 쿨다운 60초**(이메일 폭탄 방지). JWT 서명 토큰 방식도 검토했으나, 재발송 시 이전 토큰 무효화·1회성 강제에는 결국 서버 측 상태 저장이 필요해 이미 스택에 있는 **Redis TTL 방식**이 더 단순·적합하다고 판단

### FR-4 결과 시각화·검수

- 이미지 뷰어에 탐지 결과 오버레이, confidence 임계값 슬라이더
- 점검자가 오탐 삭제/누락 추가/등급 수정 가능(휴먼 인 더 루프)
- **수정 이력 구조화**: `defects` 직접 UPDATE 대신 `defect_revisions` 테이블에 append-only 기록(누가·언제·무엇을 변경) — 검수의 감사 추적 보장, 삭제는 Soft Delete
- **하자 상태머신(4단계)**: `신규(AI탐지) → 검수확정 → 조치중 → 조치완료` 표준 전이만 허용(역방향·건너뛰기는 사유 기록 필수). 상태 전이 API = `PATCH /api/defects/{id}/status`
  - **`조치대기`(`ACTION_PENDING`)는 V22에서 제거**됐다(#1072/#1083/#1097, `V22__collapse_defect_status_action_pending.sql`). "검수는 끝났고 조치는 아직"이라는 상태를 `검수확정`(`CONFIRMED`)이 그대로 겸하므로 단계를 따로 둘 실익이 없었고, 실사용에서도 두 상태의 구분 기준이 사람마다 달랐다. 기존 `ACTION_PENDING` 행은 마이그레이션에서 `CONFIRMED`로 백필한다.
  - enum 정본은 `core/defect/entity/DefectStatus.java` = `DETECTED · CONFIRMED · IN_PROGRESS · RESOLVED`
- **하자 관리 화면 재해석(v0.5, 2026-07-24 확정)**: 하자 단건 목록이 아니라 **점검(Inspection) 단위 그룹 목록**(`GET /api/inspections` — 페이지네이션, 로우 = 점검일·시설물·하자건수·등급분포) → **점검 상세(카드형 하자 그리드 + KPI 4종 헤더) → 하자 상세 풀스크린 모달** 2단계 진입
- **조치 결과 등록(v0.5 신규)**: 조치후사진·조치내용·조치일·담당자 4필드 폼 → `PATCH /api/defects/{id}/action` — 상태 전이(`/status`)와 **의도적으로 분리**한 별도 엔드포인트. 담당자 드롭다운은 `GET /api/facilities/assignable-users` 재사용(회사 소속·cross-company IDOR 검증)
- **조치 등록 이력 append-only(v1.0 신규)**: `defects`의 조치 4필드는 **"최신 스냅샷"만 담는 단일 값 컬럼**이라, 조치중(`IN_PROGRESS`) 단계에서 시간차를 두고 여러 번 등록하는 사진·조치내용이 **매번 덮어써지고 이력이 남지 않았다**. `defect_revisions`는 필드 변경 감사용(구/신 값이 짧은 문자열)이라 사진 URL을 담기에 스키마가 맞지 않아, **조치 등록 제출 자체를 통째로 append하는 `defect_action_logs` 테이블을 신설**했다(`phase` = `IN_PROGRESS`/`RESOLVED` 2단계 구분)
- **활동 기록 타임라인(v0.5)**: 감사용 `defect_revisions`를 화면에 노출 — 상태 변경·담당자 배정·조치 내용을 사용자용 타임라인 UI로 표시(v1.0: 조치 등록분은 `defect_action_logs` 기반으로 다회 이력까지 표시 가능)

### FR-5 LLM 보고서 생성 (LangChain)

- LLM: **Qwen3-8B (Apache 2.0) — HuggingFace Serverless Inference API** 호출 (종량제, HF PRO 구독)
- LangChain 체인 구성: 시설물 정보 + 확정 하자 목록·통계 → 보고서 생성 프롬프트 → LLM
- **템플릿 채우기 방식**: 자유 서술이 아닌 섹션별 짧은 생성 → 조립 구조로 sLLM 품질 편차 방어
- RAG: 점검 지침·법규 문서(Chroma Retriever) 근거 인용
- **Grounding Check(사실 검증)**: 생성 체인 마지막에 후처리 검증 단계 — LLM이 언급한 하자 개수·등급을 `defects` 실측치와 코드로 대조, 불일치 시 해당 섹션 재생성 또는 편집 가능한 초안에 경고 배지 표시(sLLM 수치 환각 방어). PDF 확정은 검증 `PASS` 결과만 허용하며, `WARN` 결과는 수정·재생성 후 재검증한다.
- **섹션 병렬 생성**: 독립 섹션(개요/요약/상세/권고)은 `RunnableParallel`로 동시 호출 — 순차 대비 지연시간 단축(100장 10분 목표 대응)
- **LangGraph StateGraph 오케스트레이션(v0.5 도입, #703)**: grounding 결과에 따른 섹션 재생성(재시도)을 손으로 짠 `while` 루프 대신 **노드 + 조건부 엣지(그래프 cycle)**로 재구성. `detail_validation ⇄ detail_retry`·`grounding_check ⇄ summary_retry` 2개 사이클, 최대 2회 재시도(`recursion_limit=20` 명시), 소진 시 기존 동작과 100% 동일(detail은 `ValueError`, summary는 `grounding_ok=False`로 진행). 재시도가 LangSmith 트레이스·`draw_mermaid()`에 개별 단계로 드러남. `get_llm()`/`check_grounding()`는 노드 본문에서 런타임 호출(모듈 캐싱 금지 — 테스트 `@patch` 호환), checkpointer 미사용(무상태 단발)
- 출력: 점검 개요, 하자 현황 요약표, 유형별 상세, 조치 권고, 종합 의견 → 편집 후 PDF 내보내기
- **생성 파이프라인 방어로직(v0.5 실측 — 구현이 PRD 초안보다 강함)**:
  - **프롬프트 인젝션 방어**: 사용자 입력에 섞인 악성 지시문이 시스템 프롬프트로 오인되지 않게 격리
  - **인용(법 조문) 검증**: LLM이 실제 참조하지 않은 조문을 인용한 것처럼 쓰지 못하게 코드로만 근거 검증(환각 인용 차단)
  - **백엔드 프록시**: 프론트가 AI 서버를 직접 호출하지 않고 백엔드가 대행 — 인증·에러코드 통일
  - **이중 Rate Limit**(사용자 단위 + 전체 단위) + **백엔드↔AI 서버 내부 인증 헤더**(별도 키)
  - **타임아웃 세분화**: 연결 실패와 응답 지연을 구분 처리
  - **RAG 폴백 견고성**: RAG 검색이 인프라 문제로 실패했을 때만 조용히 폴백, 코드 버그면 그대로 표면화(숨김 금지)
  - **LLM 클라이언트 재시도 + 캐시 스키마 불일치 시 자동 삭제**
- **보고서 저장·확정(v0.5 실측)**: `reports`는 **DRAFT/FINALIZED 상태 관리** + 같은 점검에 다중 버전 방지 **DB 유니크 제약** + **JPA 낙관적 락**. PDF는 **매직넘버 검증**, Grounding 미통과 보고서는 **확정 차단**, PDF 다운로드 URL **소유권 재검증**, 저장 경로 **path traversal 차단**, AI 응답 대기 중 **DB 커넥션 미점유**(커넥션 풀 고갈 방지)

### FR-6 RAG 챗봇 (LangChain)

- 시설물안전법·안전점검 세부지침 등 문서 임베딩(Chroma), LangChain RetrievalQA 파이프라인
- 점검 기준·법규 질의 **전담** (데이터 질의는 하자 관리 "자연어 검색"으로 일원화 — 기능 중복 방지), 답변 출처 표시
- 대화 이력 관리(LangChain Memory + Redis)
- **LLM 응답 캐시**: 프롬프트 해시 키 기반 Redis 캐시 — 개발·테스트 중 동일 질의 반복 호출로 인한 HF 크레딧 소진 방지
- **LangGraph StateGraph 오케스트레이션(v0.5 도입, #710)**: 단발 파이프라인(`cache_check → retrieve → answer → build_sources → cache_write`)을 그래프로 감싸고 조건부 엣지 2곳 적용 — 캐시 히트 시 즉시 종료, 검색 0건이면 `no_result`(캐시 저장 생략, `RAG_NO_RESULT` 응답). 멀티턴·재검색 루프는 후속 범위로 미포함(YAGNI)

### FR-7 상담 챗봇 & 상담원 연결

- **시나리오 챗봇**: 버튼 기반 플로우(예: 서비스 이용 방법 / 분석 결과 문의 / 요금·기타) — 시나리오는 관리자 페이지에서 등록·수정. 진입은 **전역 플로팅 버튼(우하단)**, 고객지원 메뉴는 이력 조회 중심

## 6. 시스템 아키텍처

**아키텍처 결정: 모놀리식** (Spring Boot 단일 앱 + FastAPI). JEUS 미사용 — Nginx가 Spring Boot 내장 Tomcat으로 직접 프록시.

```
[React SPA (Axios, WebSocket)]
      │ HTTPS / WSS
[Nginx (80/443)]
  ├─ React 정적 빌드 서빙 (/)
  ├─ /api/** ─▶ Spring Boot:8080 (리버스 프록시)
  └─ /ws/**  ─▶ Spring Boot:8080 (WebSocket 업그레이드 프록시)
      │
[Spring Boot 단일 앱 (JDK17, 내장 Tomcat, 8080)]
  ├─ 인증: OAuth2 (Kakao/Google) + Spring Session ─ Redis
  ├─ 실시간 상담: WebSocket/STOMP (상담원 연결)
  ├─ 업무 데이터 ─ PostgreSQL (사용자, 시설물, 점검, 하자, 보고서, 상담, 결제)
  │    · 스키마 변경 = Flyway forward migration (V1~V34, ddl-auto=validate)
  ├─ 결제 ─▶ [토스페이먼츠 API] (샌드박스 — 주문/승인, §2.4)
  └─ 추론/생성 요청 ─▶ [FastAPI (Python, 8000 — 내부 네트워크 전용)]
                        ├─ DL 모델 (하자 탐지 — 클래스별 2모델)
                        │    · 균열: U-Net(resnet34) 시맨틱 세그멘테이션
                        │    · 박리박락·철근노출: YOLOv8-seg
                        ├─ OCR (사업자등록증 — rapidocr)
                        ├─ LangChain + LangGraph (보고서 생성·RAG 챗봇 = StateGraph 오케스트레이션)
                        │    · LangSmith 트레이싱(관측) — get_llm() 자동 계측, env 주입, PII 제외
                        ├─ LLM: Qwen3-8B — HuggingFace Serverless Inference API
                        │    (종량제, HF PRO 구독)
                        └─ Chroma VectorDB — FastAPI 내 임베디드 모드(로컬 파일 저장)
                             임베딩: HuggingFace 한국어 모델(ko-sbert / BGE-m3, CPU — 무료)
[파일 스토리지] 업로드 원본·썸네일·오버레이 이미지
```

- **모듈러 모놀리스**: Spring Boot 내부 패키지를 도메인별(auth / core / counsel / admin)로 엄격 분리 — 향후 서비스 분리 가능한 구조로 설계
- **ORM: Spring Data JPA(Hibernate)** — Entity·Repository 규약은 `SpringBoot_코드_컨벤션.md` 참조. 프론트 규약은 `React_코드_컨벤션.md` 참조
- **이메일 발송: Spring Boot Starter Mail(SMTP)**(v0.45 신규) — 회원가입·아이디 찾기·비밀번호 찾기 인증코드 발송 전용. 실제 발송은 비동기 처리(`@Async`)로 API 응답 지연 방지
- **프론트엔드 공통 UI 스택**(v0.44): 스타일링은 **Tailwind CSS 4.3.2**로 통일, 대시보드·통계·회차 비교 등 화면 전반의 차트·그래프는 **Recharts 3.9.2**를 공통 컴포넌트로 사용(개별 화면별 차트 라이브러리 혼용 금지)
- Spring Boot ↔ FastAPI: REST + 비동기 잡 패턴(분석 요청 → 잡 ID → 폴링/콜백). FastAPI·DB·Redis·Chroma는 외부 포트 미개방(내부 통신 전용)

### 6.1 배포 환경 — OCI (Oracle Cloud Infrastructure)

> **📌 실배포 현황(2026-07-16, #258·#260) — 아래 "전용 VM 단일 호스트"는 목표(prod/향후)이고, 현재 dev 배포는 공유 호스트다.**
> A1 전용 VM 확보 전까지 dev는 **oci-arm1 공유 호스트**(hajacheck 외 7개 사이트와 공존)에서 운영한다. 공유 호스트에선 80/443이 호스트당 1개뿐이라 하자첵 nginx가 이를 독점할 수 없다 → **유일한 PRD 이탈 = "엣지 80/443 TLS 종료 nginx가 공용 host nginx"** 1건. 나머지(내부 bridge 네트워크·전용 postgres/redis 컨테이너·dev/prod DB 분리·이미지 SHA 태그)는 모두 준수하며, 하자첵 전용 nginx 컨테이너는 그 뒤 `127.0.0.1:8100`에서 앱 라우팅(/api·/ai·/ws·정적)을 담당한다(`docker-compose.arm1.yml`, 2026-07-16 B안 확정).
> - **dev/prod 분리**: 현재 arm1 = **dev 전용**(DB `hajacheck_dev`, Redis 인덱스 1). `hajacheck_prod`는 예약, **prod 실배포는 전용 VM 확보 시** 아래 이상형대로 이관.
> - 전용 VM 확보 시 아래 구성(nginx 포함 전 구성요소 compose, 80/443 독점)을 그대로 적용하면 이탈 0.

**인프라: OCI Always Free — Ampere A1 VM 1대 (ARM/aarch64, 3 OCPU / 16GB RAM, Ubuntu 22.04)**

```
[도메인 DNS] ── A레코드 ──▶ [OCI Reserved Public IP(고정)]
                                    │
[OCI VCN — 퍼블릭 서브넷, Security List: 80/443/22만 개방]
 └─ Ampere A1 VM ─ Docker Compose (단일 호스트, 내부 bridge 네트워크 1개)
     ├─ nginx    :80/:443 — React dist 서빙, 리버스 프록시, certbot(TLS 종료)
     ├─ spring   (내부) — nginx가 /api·/ws 프록시
     ├─ fastapi  (내부) — nginx가 /ai 프록시, 외부 차단. YOLOv8-seg 추론(CPU) + Chroma 임베디드(볼륨)
     ├─ postgres (내부) + 127.0.0.1:5432 publish — 팀 SSH 터널 전용
     └─ redis    (내부) + 127.0.0.1:6380 publish — 팀 SSH 터널 전용, requirepass·AOF
   volumes: pgdata · redisdata · chroma_data · certbot 인증서
```

- **서버 구성 = Docker Compose 단일 호스트**: 전 구성요소를 compose 서비스로 관리(내부 bridge 네트워크, 외부 노출은 nginx 80/443만). ARM(aarch64) 호환은 검증됨 — 베이스 이미지 전부 multi-arch, ML 의존성(torch·onnxruntime)은 aarch64 사전빌드 휠 사용, Redis는 이미 컨테이너로 운영 중. Chroma는 임베디드 모드(볼륨 파일 저장) 유지 → 별도 프로세스 없음.
- **이미지 버전 = 레포 추종**(단일 진실): Dockerfile은 `build.gradle`(Java 17·Gradle 8.14.3)·`requirements.txt`·`package.json`(Vite 6·React 18)을 그대로 빌드하고 버전을 중복 명시하지 않는다. 이미지 태그는 `latest` 금지 — 버전+커밋 SHA 병행. 멀티스테이지·non-root `USER`·`.dockerignore`·`HEALTHCHECK`·`depends_on: condition: service_healthy` 적용.

**개발 환경 — 공용 개발 DB (SSH 터널 접속)**

- OCI 서버의 PostgreSQL·Redis **컨테이너**를 **팀 공용 개발 DB**로 사용. 포트는 공개하지 않고 **SSH 터널 전용 계정(`hajadev`, permitopen 5432·6380 제약)**으로만 접속 — `application-local.yml`에 터널 로컬 포트 설정. 컨테이너는 호스트 `127.0.0.1:5432`·`:6380`에 publish → 터널 대상 주소가 불변이라 **Docker 전환 후에도 팀원 재온보딩 불필요**. (로컬은 필요 시 동일 compose로 재현)
- **보안 필수 조치**:
  - 5432·6380은 **공개 미개방** — OCI Security List는 80/443/22만. DB/Redis는 SSH 터널로만 도달
  - PostgreSQL: 강력한 비밀번호, 컨테이너는 내부 bridge 네트워크에만 노출
  - Redis: `requirepass` 필수 설정(미설정 시 인증 없이 전체 접근 가능) + AOF
- **개발/운영 분리**: PostgreSQL은 `hajacheck_dev` / `hajacheck_prod` 데이터베이스 분리, Redis는 DB 인덱스 분리(운영 0번 / 개발 1번)
- 팀 규칙: 공용 dev DB의 스키마 변경(DDL)은 사전 공지 후 진행. **개발 DB에 실사용자 데이터 저장 금지** — 시연·테스트용 합성 데이터만 사용(개인정보가 팀원 전원의 로컬 접속 구간에 노출되는 것 방지)
- 저장소의 compose 정의는 **정식 배포 수단**(운영·로컬 공용): `docker-compose.yml`(base) + `docker-compose.override.yml`(로컬 개발, 핫리로드) + `docker-compose.prod.yml`(운영). 오프라인·파괴적 테스트도 동일 정의로 격리 실행
- 방화벽 이중 설정 주의: OCI Security List + VM 내부(ufw/iptables) — 공개는 80/443/22만
- Nginx WebSocket 프록시 설정(`Upgrade`/`Connection` 헤더) 필수 — 상담 기능 전제조건
- 보안: SSH 키 인증, 외부 노출은 nginx 80/443만, DB(5432)·Redis(6380)는 SSH 터널 전용(미개방), fastapi는 내부 네트워크 전용
- LLM(HF Serverless API)은 외부 API 호출이라 서버 사양 무관, YOLO 추론은 ARM CPU로 수행(데모 수준 충분)

**CI/CD: GitHub Actions**

- CI (PR 시): Spring Boot 빌드+테스트, FastAPI 테스트, React 빌드 — path filter로 변경 파트만 실행 (네이티브 실행, 현행 유지)
- CD (main 승격 시): VM에 SSH → `git pull && docker compose build && docker compose up -d`. **ARM 이미지는 VM에서 직접 빌드**(VM 자체가 aarch64 → 크로스빌드·외부 레지스트리 불필요), BuildKit 레이어 캐시로 재빌드 최소화. 코드는 빌드 시 이미지에 baked-in(COPY), 데이터는 볼륨에 영속. 배포 후 `HEALTHCHECK`로 기동 확인
- SSH 키·서버 IP 등은 GitHub Secrets 관리

**리스크 대비**

- A1 무료 인스턴스는 리전 용량 부족("Out of capacity")이 잦음 — **착수 주간(7/9~13)에 선확보**, 실패 시 PAYG 전환(Always Free 한도 내 과금 없음)
- **시연 백업 플랜**: 완료보고(8/7) 당일 로컬 실행 환경 — 동일 compose로 그대로 재현 가능(별도 준비 최소화)

### 6.2 AI 개발 컨벤션 (전원 AI 구현 체제의 품질 통일 장치)

> 상세 실무 규약은 별도 문서 **`AI_개발_컨벤션.md`** 참조 (디렉토리 구조, 코드 예시, 개발 절차, 리뷰 체크리스트 포함)

각 메뉴 담당이 AI 기능을 직접 구현하되, 아래 공통 기반 위에서만 개발한다. AI-LLM 코치가 공통 모듈(`llm_client`)·컨벤션 문서·예시 체인 1개·온보딩 발표자료를 **작성 완료**(2026-07-13 기준) — 온보딩 세션(7/15)에서 배포하고, 코드 리뷰 ①(7/17)에서 준수 여부를 점검한다.

1. **공통 LLM 클라이언트 단일화**: FastAPI에 `llm_client` 공통 모듈(모델명·HF 엔드포인트·타임아웃·재시도·토큰 사용량 로깅 일원화). 모든 체인은 이 클라이언트만 사용
2. **프롬프트 파일 분리**: 하드코딩 금지, `prompts/` 디렉토리에 파일 관리(`report_summary.md`, `defect_explain.md` 등), 공통 시스템 프롬프트 템플릿 사용
3. **출력 형식 통일**: LLM 응답은 JSON 스키마 지정(structured output)으로만 수신 — 자유 텍스트 파싱 금지
4. **엔드포인트·에러 규약**: AI 엔드포인트 네이밍 통일(`/ai/report`, `/ai/chat`, `/ai/nl-search` 등), 요청/응답 공통 포맷, 실패 시 표준 폴백 처리
5. **버전 고정**: LangChain·chromadb 등 requirements 버전 고정 (LangChain은 버전 간 API 변화가 큼). **v0.5 조합: `langchain==0.3.30` + `langchain-core==0.3.86` + `langsmith==0.10.10` + `langgraph==0.6.11`** — 병렬 브랜치가 `langgraph`만 단독 추가하면 pip `resolution-too-deep`이 나므로, 공용 `requirements.txt` 조합을 반드시 동일하게 맞춘다. **`requirements.txt` 변경 PR은 PR봇 자동 머지 제외 — 사람 확인 후 수동 머지**(의존성 설치 = 코드 실행)
6. **법규 문서 청킹**: 임의 글자수 분할 금지 — 법조문 경계 우선 분리자 사용(`RecursiveCharacterTextSplitter(separators=["\n제", "\n①", "\n\n", "\n"])`) — 조문 중간 절단은 출처 인용 정확도(KPI) 저하 직결
7. **AI 오케스트레이션(LangGraph, v0.5)**: 재시도·조건분기가 있는 체인(보고서 생성 FR-5, RAG 챗봇 FR-6)은 손으로 짠 `while`/`if` 대신 **LangGraph StateGraph(노드 + 조건부 엣지)**로 구성 — 사이클이 있으면 `recursion_limit` 명시, 그래프는 모듈 로드 시 1회 compile, 무상태 단발이면 checkpointer 미사용. LangGraph 리팩터는 "테스트 통과"만으로 검증 부족 → 재시도 횟수를 mock `call_count`로, 그래프 구조를 `draw_mermaid()`로 직접 확인(재시도 상한 조용히 축소되는 회귀 방지)
8. **AI 관측(LangSmith, v0.5)**: `get_llm()`이 전 체인의 유일한 LLM 호출 지점이라 환경변수(`LANGCHAIN_TRACING_V2` 등 4개)만으로 자동 트레이싱 — 프롬프트·소요시간·토큰·응답이 LangSmith `hajacheck` 프로젝트에 트리로 기록. docker-compose `fastapi` 서비스에 soft-default로 연결(값 없으면 비활성), 키는 env 주입(코드·로그 평문 금지)
9. **관측 페이로드 PII 제외(v1.0 신규)**: LangSmith는 **외부 SaaS로 프롬프트 전문이 전송**되므로, 트레이싱 대상 페이로드에서 개인정보(이메일·사업자등록번호·전화 등)를 **제외·마스킹**한다 — 관측 편의를 위해 개인정보를 제3자에 넘기지 않는다는 원칙(§5 개인정보 원칙과 정합). 회귀 방지용 전용 테스트를 둔다(체인 추가 시 PII가 슬며시 트레이스에 실리는 것을 차단)

> DL 추론은 AI-DL 담당의 단일 엔드포인트를 호출하는 구조라 별도 컨벤션 불필요.

**기술 영역별 담당 — 풀스택 챕터제 (메뉴 횡단 기술 축, 9챕터)**

레이어(FE/BE) 분업이 아닌 **관심사(챕터) 기준** — 모든 챕터가 화면부터 서버까지 관통하므로 누구나 풀스택 경험을 갖는다. 챕터 담당은 해당 기술 영역의 표준·규약을 정하고 코드를 리뷰하는 오너. **메뉴 담당(기능 축)과 매트릭스 교차 운영** — 주/부담당은 그 기술을 실제로 쓰는 메뉴 오너에서 도출. 챕터 9(DevOps)는 특정 메뉴에 속하지 않고 전 챕터를 관통하는 플랫폼 운영 레이어(정재봉 고유 영역).

    - **승인 응답 유실 복구 경로**: "첫 승인 요청이 PG에 도달해 실제 승인됐으나 응답만 유실된" 경우, 재시도로는 복구되지 않고(PG가 중복 처리 코드만 반환) 재시도 소진 후 주문이 취소로 닫혀 **실제 청구를 은폐**할 수 있다. 샌드박스에선 실청구가 없어 발동 조건 자체가 없으나, 라이브에서는 "돈은 받고 요금제는 미지급 + 원장은 취소" 상태가 된다 → **라이브 전환 전 필수 해소**
    - **결제창 E2E 실검증**: 현재까지 검증은 테스트 코드·목서버 기준이며 실제 결제창→리다이렉트→승인 전 구간을 통과시켜본 적이 없다(successUrl/failUrl 수용 여부, 실 승인 응답 필드와 DTO 매핑 일치)
    - 정기 자동결제(빌링키)·환불·대사(정산 대조) 범위 확정
14. **하자 등급 임계값 DB화 시점**(v1.0 신규) — 임계값은 현재 상수 모듈 하드코딩이고, DB화 UI로 예정돼 있던 "하자 유형·등급 기준 관리" 메뉴는 v1.0에서 **삭제**됐다. 재측정이 모델·전처리·집계 조건에 묶여 있어 운영자 임의 변경이 위험할 수 있으므로, **DB화 여부 자체를 재검토**(운영 편의 vs 캘리브레이션 정합성)
