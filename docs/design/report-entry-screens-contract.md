## 0. 3분류 ↔ 실제 화면 매핑

| 분류 | 화면 | 라우트 |
|---|---|---|
| 생성 | `ReportEntryPage` | `/inspections/:id/reports` |
| 조회 | `ReportListPage` (회사 스코프 전체 목록) | `/reports` |
| 편집·출력 | `ReportGeneratePage` (편집 + 확정(finalize) + PDF 저장이 한 화면에 결합) | `/inspections/:id/reports/generate?reportId=X` |

## 1. 활성 점검 없을 때 fallback·빈 상태

사이드바 메뉴 소속에 따라 fallback이 다르다(`SideNavBar.tsx`):

| 메뉴 | 소속 그룹 | 활성 점검 없을 때 |
|---|---|---|
| 보고서 생성 진입점 | 점검 관리 | `/inspections/create` (점검 생성으로 유도, #938) |
| 보고서 편집·미리보기 / PDF 내보내기 | 보고서 | `/reports` (목록으로 — 편집 대상은 특정 reportId라 활성 점검 유무와 무관) |
| 보고서 목록/이력 관리 | 보고서 | 항상 `/reports` (회사 스코프, 점검 상태 무관) |

목록 0건 문구는 이미 구현됨: `ReportListTable`의 `emptyMessage="조건에 맞는 보고서가 없습니다"`.

## 2. 활성 점검 있을 때 inspection id 전달 방식

라우트 path param으로 고정 전달: `/inspections/:id/reports`(생성), `/inspections/:id/reports/generate?reportId=X`(편집, reportId는 query param). `ReportListTable` 각 행도 `inspectionId`를 갖고 있어 목록→편집 이동 시 동일 패턴(`/inspections/${row.inspectionId}/reports/generate?reportId=${row.id}`)을 쓴다.

하자 상세(`DefectListPage`) "보고서 생성" 버튼은 진입점으로 직행하지 않고 결과뷰어(`/inspections/{id}/viewer`)를 한 번 거쳐서 간다 — inspectionId는 동일하게 전달되지만 경유 화면이 하나 더 있다(§6 결정 필요 지점).

## 3. 생성 후 목록/편집 화면 이동 규칙

생성 성공(`POST /api/inspections/{id}/reports`) 시 응답의 `id`로 즉시 `/inspections/{id}/reports/generate?reportId={새 reportId}`로 이동 — 목록 화면을 거치지 않고 편집 화면 직행. 진입점의 "최근 작업 내역"에서 기존 초안을 이어서 편집할 때도 동일 규칙(reportId만 다름). 목록 화면(`ReportListPage`)은 사이드바를 통한 별도 진입만 있고, 생성 흐름 중 자동으로 이동하는 지점은 없음.

## 4. 버전 이력 플라이아웃

목록 화면(`ReportListPage`) 우측에서 열리는 슬라이드 패널(`ReportVersionHistoryPanel`) — 행의 ⋮ 메뉴 "버전 이력" 클릭으로 진입(`onOpenVersionHistory`). 버전별 비교(diff)·되돌리기 제공. 되돌리기는 `DRAFT` 상태에서만 허용, `FINALIZED`는 차단 문구("완료된 보고서는 되돌릴 수 없습니다")로 막는다. 새 엔드포인트 없이 기존 `GET/PATCH /api/reports/{id}`를 재사용.

## 5. 일괄 내보내기 진입점

목록 화면 헤더 우측 "내보내기(일괄)" 버튼. 체크박스로 여러 행 선택 → `FINALIZED` + `pdfUrl` 보유 행만 실제 대상으로 필터링(나머지는 버튼 비활성 + title 안내). 진행 중 "내보내는 중…", 완료 후 "N건 내보냈습니다" / "N건 내보냄 · N건 실패" 메시지 노출.

## 6. AI 초안·법정 제출용 아님 고지 위치

이미 2곳에 구현되어 있다:
- **생성 화면**(`ReportEntryPage`) — 보고서 설정 블록 안, 액션바보다 위(#463 요구항목 반영)
- **편집 화면**(`ReportGeneratePage`) — 상단 경고 배너(#463 후속)

**목록 화면(`ReportListPage`)에는 없음** — 조회 단계에도 고지가 필요한지는 미정(§6 결정 필요 지점).

## 7. 결정이 필요한 지점 (김관영 확인 요청)

1. **사이드바 3분류 되돌림 이력** — PR #943에서 "생성/조회/편집·출력" 재분류가 Figma 미대응으로 되돌려진 바 있음. 지금 요청하신 3분류가 사이드바 라벨 재변경까지 포함하는지, 화면·API 계약 차원의 개념 분류인지 확인 필요.
2. **목록 0건 문구의 두 상황 구분** — "진짜 빈 상태"(보고서 자체가 하나도 없음)와 "필터로 걸러진 0건"이 현재 같은 문구("조건에 맞는 보고서가 없습니다")를 공유. 구분할지 여부.
3. **하자 상세 → 결과뷰어 경유** — "보고서 생성" 버튼이 진입점 직행이 아니라 결과뷰어를 거치는 현재 흐름을 유지할지, 진입점으로 바로 보낼지.
4. **목록 화면의 AI 초안 고지 여부** — 조회 단계에도 배너를 추가할지.

## 7-1. 추가 질문 답변 — "편집" 사이드바 메뉴가 특정 reportId로 직행해야 하는지 (관영 2026-07-27 회신)

현재 코드(`SideNavBar.tsx`) 기준 사실:
- "보고서 편집·미리보기"·"PDF 내보내기" 두 메뉴는 **특정 reportId로 직행하지 않는다.** 활성 점검이 있으면 `/inspections/{id}/reports`(=생성 화면인 `ReportEntryPage`와 동일 페이지)로 이동하고, 그 페이지의 "최근 작업 내역" 목록에서 "이어서 편집"을 눌러야 비로소 특정 reportId로 진입한다.
- 활성 점검이 없으면 `/reports`(회사 전체 목록)로 가서 행을 클릭해야 reportId가 정해진다.
- 즉 두 메뉴 다 현재는 "목록에서 선택" 방식이고, 동시에 **"편집·미리보기"와 "PDF 내보내기"가 활성 점검이 있을 때 같은 화면(생성 화면)으로 가는 중복 상태**(§0 라우트 재확인 시 발견).

이 사실 자체는 1번 결정(사이드바 라벨 재편)과 함께 정리하면 될 것으로 보임 — 별도 대응 불필요.

## 8. 실데이터 검증 범위 (제약 재확인)

공유 dev DB에 점검·하자·보고서 실데이터가 없어 정상 목록·PDF 다운로드 실검증은 현재 불가. 위 화면 계약·목(MSW mock) 테스트는 기존 코드에 이미 구현·테스트되어 있으므로 이번 정리로 충분하고, 실데이터 검증은 데이터 확보 후 별도 진행.
