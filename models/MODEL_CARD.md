> **2026-07-28 갱신** — 학습·평가가 끝나 값이 확정됐다. 착수 시점의 "YOLOv8-seg 단일 모델" 전제는 실제 구성과 달라 §2를 개정했다: 균열은 선형 하자라 객체탐지가 부적합해 **U-Net으로 교체**했고, 지금은 **하자 유형별 전용 체크포인트 3개**를 병합 호출한다.

## 1. 파일명·버전 규칙 (확정)

- **가중치 파일명**: `{날짜}_{데이터셋버전}_{mAP}`
  - 예: `20260710_v1_0.71` (2026-07-10 학습 · 데이터셋 v1 · mAP@0.5 0.71)
  - `{날짜}`=`YYYYMMDD`, `{데이터셋버전}`=`v1`·`v2`…, `{mAP}`=`mAP@0.5` 소수 둘째자리
- **MLflow run 이름**: `{날짜}_{데이터셋버전}` — `ai-dl/tracking.py`의 `_run_name()`과 **동일 규칙**(mAP는 run 이름엔 없고 메트릭으로 기록). 파일명은 여기에 `_{mAP}`만 덧붙인 형태.
- **산출물 배치**: 학습 산출물(`.pt` → ONNX 변환 `.onnx`)은 `models/{파일명}/`에 두고, 이 카드에 해당 버전 행을 추가한다. (가중치 바이너리 자체는 레포에 커밋하지 않음 — Drive/서버 배포본으로 관리)

## 2. 모델 개요 (설계 확정)

| 항목 | 값 |
|---|---|
| 태스크 | 시설물 하자 탐지 — 균열=시맨틱 세그멘테이션 / 면적형=인스턴스 세그멘테이션 |
| 아키텍처 | **하자 유형별 전용 체크포인트 2종** — 균열 `U-Net(resnet34, Dice+BCE)` · 박리·박락/철근노출 `YOLOv8n-seg` |
| 탐지 클래스 (3종 확정) | `균열(CRACK)` · `박리·박락(SPALLING)` · `철근 노출(REBAR_EXPOSURE)` — 2026-07-13 데이터셋 라벨링 기준 |
| 제외 (후속 확장) | 누수·백태, 도장 손상 (데이터 확보 상황상 이번 범위 제외) |
| 성능 목표 | **균열 = IoU · Recall 기준**(아래 주 참조) · 면적형 = 클래스별 mAP50-95 · Recall 개별 리포트 |
| 서빙 | 저장소 `50seok/hajacheck-defect-detection`(HF Hub) — 파일명 **고정 매핑**으로 3개 체크포인트를 각각 로드해 결과 병합. 기동 시 전부 워밍업 |
| 추론 배포 | 학습=로컬 GPU, 서버=**추론만** 배포(ultralytics `.pt` raw PyTorch) |

> **성능 목표를 mAP@0.5 → IoU·Recall로 개정한 이유**: 착수 목표(`균열 mAP@0.5 ≥ 0.70`)는 YOLOv8-seg 전제로 세운 값인데, 균열 모델이 U-Net(시맨틱 세그멘테이션)으로 바뀌며 **인스턴스 단위 mAP를 산출할 수 없게 됐다**. 지표를 억지로 맞추기보다 픽셀 단위 IoU와 Recall로 목표를 다시 세우는 것이 맞다. **Recall을 주지표로 두는 것은 안전점검의 성격 때문** — 놓친 하자(FN)가 오탐(FP)보다 위험하다.
> ⚠️ PRD §FR-3의 KPI 문구도 같은 이유로 개정 대상이다(후속).

### 2.1 체크포인트 파일 매핑 (`ai-server` 실값)

| 하자 유형 | 체크포인트 | 로더 |
|---|---|---|
| `CRACK` | `crack_unet_resnet34.pt` | `ai/core/unet_client.py` |
| `SPALLING` | `spalling_yolov8n_seg.pt` | `ai/core/yolo_client.py` |
| `REBAR_EXPOSURE` | `rebar_exposure_yolov8n_seg.pt` | `ai/core/yolo_client.py` |

> 파일명을 코드에 **고정 매핑**한다. 과거처럼 저장소의 `.pt`를 자동 탐색해 첫 파일을 집으면, 저장소 구조가 유형별로 바뀐 순간 ultralytics 포맷이 아닌 U-Net 파일을 로드해 `KeyError: 'model'`로 실추론이 전면 중단된다(#991).
> 구버전 `crack_yolov8s_seg.pt`는 참고용으로 저장소에 남아 있으나 **서빙에 쓰지 않는다**.

## 3. 학습 데이터

| 항목 | 값 |
|---|---|
| 출처 | AI Hub 「건물 균열 탐지 이미지」 등 |
| 규모 | 약 **161,000장** 확보 완료 |
| 데이터셋 식별자 | `haja19_dataset` (Colab 학습용 Google Drive 업로드 완료) |
| 데이터셋 버전 | v1 (1차 학습 기준) |
| 전처리 (균열) | `LongestMaxSize(640) + PadIfNeeded` 레터박스 + ImageNet 정규화 — **추론(`unet_client.py`)이 학습(`train_crack_unet.py`)과 동일 조건**이어야 한다 |
| 분할 | **촬영건(scene) 단위 분할** |

> **무작위 분할을 쓰지 않는 이유(데이터 누수)**: AI Hub 데이터는 같은 벽·구조물을 연속 촬영한 프레임이 많아, 무작위로 나누면 거의 동일한 사진이 train과 val에 함께 들어가 성능이 부풀려진다. 촬영건 단위로 끊어 보정하자 mAP50-95가 **0.081 → 0.069**로 내려갔다 — 떨어진 게 아니라 **부풀림이 걷힌 값**이다. 아래 성능 수치는 전부 이 보정된 기준이다.

## 4. ARM CPU 추론 최적화 (설계 확정)

> ⚠️ **현재 미적용**(2026-07-28) — 아래는 설계이고, 서빙은 아직 ultralytics `.pt` **순정 PyTorch 직접 추론**이다. 따라서 "100장 10분" KPI는 ONNX 전제가 아닌 현재 구성으로 arm1(3코어 ARM CPU)에서 실측해야 한다(미측정).

- 학습 산출물에 **ONNX 변환 + INT8 양자화** 파이프라인 포함 → ONNX Runtime 서빙.
- 순정 PyTorch 대비 **2~4배 속도** 확보 (100장 10분 목표의 전제).
- FastAPI 워커 분리: CPU-bound YOLO 추론은 별도 워커 프로세스로 오프로드(3 OCPU: 탐지용 1 + API용 1~2).

## 5. 하이퍼파라미터

| 항목 | 균열 (U-Net) | 면적형 (YOLOv8n-seg) |
|---|---|---|
| 손실 | Dice + BCE | ultralytics 기본 |
| 입력 해상도 | 640×640 (레터박스) | 640 |
| 학습 epoch | 30 (**best = epoch 14**) | — |

> **조기 수렴**: 30 epoch를 돌렸으나 epoch 14 이후 IoU·F1·Recall이 모두 개선 없이 진동했다. 이후 학습은 반복 비용만 든다.
> 나머지 상세(batch·optimizer·lr·증강)는 MLflow run에 자동 로깅된다 — 실험 이름 규칙은 §1 참조.

## 6. 성능 (2026-07-27 실측 · 촬영건 단위 분할 기준)

| 하자 유형 | 모델 | Recall | Precision | 주지표 |
|---|---|---|---|---|
| 균열 | U-Net (resnet34) | 0.575 | 0.629 | IoU **0.429** |
| 박리·박락 | YOLOv8n-seg | 0.679 | 0.788 | mAP50-95 **0.480** |
| 철근 노출 | YOLOv8n-seg | 0.699 | 0.811 | mAP50-95 **0.328** |

**균열 아키텍처 교체 효과**: 모델 크기 확대(n→s)·해상도 상향(640→1280)·라벨 정제를 모두 시도했으나 YOLOv8은 **recall 0.28에서 정체**했다. 선형 하자를 박스/인스턴스로 잡는 구조 자체가 맞지 않는다고 판단해 픽셀 단위 세그멘테이션으로 교체 → **recall 0.28 → 0.575 · precision 0.39 → 0.629**(약 2배).

**철근 노출**은 confidence 임계값을 조정해도 recall이 더 오르지 않는 최적 동작점이다.

## 7. 한계·주의

- 학습 데이터가 공개 데이터셋 중심이라 실제 현장 분포와 차이 가능 → 배포 후 오탐 모니터링·재학습 전제.
- 3종 외 하자(누수·백태·도장 손상)는 탐지 불가 — 검수자 수동 확인 필요.
- 심각도 등급은 모델이 아닌 **규칙 기반**(크기·유형)으로 산정(A~E 5등급) 후 점검자 수동 조정. 상세: `conventions/하자_심각도_등급_규칙.md`(HAJA-109).
- INT8 양자화로 인한 정확도 손실은 **ONNX 적용 시** FP32 대비 지표 차이로 측정·기재(현재 미적용이라 해당 없음).
- 균열 Recall 0.575는 **놓치는 하자가 40% 남는다**는 뜻이다 — 검수(휴먼 인 더 루프)를 전제로만 운용한다.
- 심각도 산정에 쓰는 `area_ratio` 밴드는 **모델·전처리·집계 3요소에 종속**된다. 모델을 바꾸면 분포가 이동하므로 밴드를 반드시 재측정한다(#953·#998에서 실제로 과대경고 발생).
